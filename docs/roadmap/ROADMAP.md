# 分阶段开发与学习路线图

版本：baseline-0.1。版本号是产品能力，M 编号是里程碑文档，M0.1.x 是 M01 内的学习步骤，不是三个互相独立的产品版本体系。

## 1. 编号统一

原产品路线有 M01～M09 对应 V0.1～V0.9，另有 V1.0 发布；后续学习建议把 PCC 单列，导致 Forecast 等学习编号顺延。本基线保留原产品版本：PCC 独立为 M03-B，V1.0 记作发布门禁 G10，避免把 V0.4 同时称为 PCC 和 Forecast。
M03-A/B 都属于 V0.3；PCC 有自己的 Demo 和人工验收，不被省略。未来 M02～M09 的详细里程碑文件按需创建，本 ZIP 只创建 M01。

## 3. 开发七步循环

1. 阅读当前阶段、产品/架构/模型/接口，检查已有代码和环境。
2. 说明本步文件、类型、数据流、依赖、测试、Demo、风险。若用户只要方案，在此交付方案。
3. 在获准范围内实现，保持可运行；不为未来功能创建无用服务或空框架。
4. 跑与改动相符的单元/契约测试。
5. 跑边界集成与负向测试，修复失败。
6. 跑可重复 Demo，展示输入、实际输出、日志/历史证据，补学习说明。
7. 标记 READY_FOR_REVIEW，由用户学习、查看差异并验收；确认后才 ACCEPTED/推进。

每个 M0.1.x 都经过此循环。子步骤是增量闭环：脚手架有可运行健康入口，模型有契约样例，Simulator 有可查询值，Gateway 有记录输出；不是要求 M0.1.1 就具备整条 M01 数据链。

## 4. 状态、记录与标签

NOT_STARTED → IN_PROGRESS → READY_FOR_REVIEW → ACCEPTED。
遇到缺少输入或环境限制可记 BLOCKED，写明问题、证据、恢复条件；失败需退回 IN_PROGRESS 修复。ACCEPTED 的判断必须含用户确认记录，不能由“测试绿了”自动获得。

CURRENT_STAGE.md 保存当前唯一阶段/步骤、授权范围、状态、验收记录和下一步。新增学习日志 `docs/learning/LEARNING_LOG.md` 保存解释与证据，不把完整测试日志塞进 AGENTS.md。
每步建议独立 commit；仅在用户授权提交时执行。里程碑验收后可按用户授权打标签：

| 里程碑 | 建议标签 |
|---|---|
| M01 | v0.1.0-kernel |
| M02 | v0.2.0-scada |
| M03-A | v0.3.0-control-alpha（仅学习检查点） |
| M03-B | v0.3.0-control |
| M04～M09 | v0.4.0-forecast / v0.5.0-dayahead / v0.6.0-intraday / v0.7.0-microgrid / v0.8.0-blackstart / v0.9.0-engineering |
| G10 | v1.0.0 |

标签用来保留已验收状态；回退应保留后续工作，不默认执行破坏性 reset。

## 5. 后续阶段规格的固定内容

每个详细里程碑都要写：学习目标、前置条件、范围、非目标、数据流、组件/路径、正常与异常测试、Demo 输入/预期输出、验收清单、完成条件、遗留风险、关联 F/A 编号。
开始后续阶段前先把该详细规格补齐；不得仅凭路线图一句话大规模实施。

## 6. 发布门禁与范围变更

G10 至少交付 EMS Server、Web UI、数据库迁移、安装包、设备模板、用户/操作/工程/API 手册、FAT/SAT 用例及结果、Release Notes、备份与回滚说明。
仍缺现场 SAT 或 7×24h 证据时，只能称候选版本，不能宣称已具备商用验收。
性能测试记录硬件与负载；7 天测试不能推出月可用率；模拟设备数量不能冒充物理接入数量。
增加需求先映射产品范围，必要时提出 V1.x/V2.0 或正式变更。对于原范围内遗漏功能，应修正阶段覆盖，而不是删除需求。
